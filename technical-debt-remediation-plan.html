Recommendation

Split behavior first, then change behavior. Begin with release/version guardrails, extract the two oversized modules behind stable facades, and only then tackle compatibility shims and CSS. Do not raise minAppVersion during the refactor, and do not remove the legacy API alias before 1.0.

The important wrinkle is that two debt items cannot honestly be “fixed” today. The installed Obsidian API exposes MarkdownView.getMode() but no public mode setter, and it exposes getDisplayText() but no public title setter or header refresh. Those hacks should be isolated, feature-detected, and made failure-safe until supported APIs exist.

Immediate regression: the repository reports version 0.7.0 everywhere except both root version fields in package-lock.json, which remain 0.6.2. This belongs in the first changeset and needs a CI check so it cannot recur.

Implementation sequence

Each phase is intended to be a separate reviewable commit or pull request. Release operations and architecture become independent after Phase 1, but keeping this order makes regressions easier to localize.

01

Install guardrails before moving code

Close the live version drift and stop release automation from manufacturing another one.

  • Add scripts/check-version-consistency.mjs to compare package.json, both lockfile version fields, manifest.json, the newest versions.json entry, and an optional release tag.
  • Add check:versions to package.json and include it in npm run check.
  • Regenerate only lockfile metadata so it records 0.7.0; do not change dependency resolution.
  • Consolidate release automation as described below; delete manual-release.yaml after parity is proven.
Acceptance

A deliberate mismatch makes local and CI checks fail with the exact files/values; normal npm run check passes; neither release trigger commits to the default branch.

02

Characterize and split Scripture list behavior

Keep scripture-list-renderer.ts as a temporary facade so main.ts and Markdown registration do not churn at the same time.

  • scripture-list-lookup.ts: translation suffix parsing, reference detection, verse lookup, testament/book enrichment.
  • scripture-list-source.ts: normalization, sorting, range resolution, and vault process() mutations.
  • scripture-list-view.ts: DOM rendering and fold-state presentation only.
  • scripture-list-clipboard.ts: clipboard input expansion and callout copy.
  • scripture-list-editor.ts: locating the owning view, switching modes, cursor placement, and retry timing.
Tests added before extraction

Translation suffixes; invalid/missing translations; chapter and range lookup; normalization and testament gaps; codeblock range selection with multiple fences; comma-separated paste expansion; copy-callout formatting. Keep DOM and Obsidian effects behind injected interfaces.

03

Reduce main.ts to the plugin shell

Move one responsibility at a time while preserving every released command ID, URI parameter, Markdown format, settings key, and API method.

  • commands.ts: registers commands from a typed dependency object; command callbacks remain behaviorally identical.
  • scripture-note-service.ts: parse, resolve, format, and open Scripture note targets.
  • plugin-settings-store.ts: load, migrate, validate cross-setting invariants, save, and notify components.
  • scripture-list-processor.ts: Markdown processor registration and orchestration.
  • public-api.ts: builds the frozen ScriptureAPI facade and owns registry compatibility.

Target: src/main.ts at roughly 200–300 lines, containing lifecycle wiring and cleanup rather than feature algorithms.

Acceptance

All existing command IDs and URI aliases are asserted; ScriptureAPI retains the same method names and return shapes; settings migration tests still pass; no circular import from services back into the plugin class.

04

Split settings without raising the minimum version

Use the supported imperative Setting API for 1.9.0. Do not build a home-grown declarative framework that will be thrown away later.

  • Keep settings.ts as a small re-export or registration surface.
  • Move translation list + TranslationModal, insertion/link sections, callout/list sections, and note/sidebar sections into focused modules under src/settings/.
  • Pass a narrow settings controller interface instead of importing the concrete Scripture class into every settings module.
  • Keep defaults and persisted types in types.ts; keep schema migrations pure in settings-migrations.ts.
Acceptance

All current controls appear in the same order with the same sentence-case text and dynamic visibility; translation add/edit/remove/validate and every immediate-refresh behavior work in the test vault.

05

Contain compatibility shims and record policy decisions

  • Create a mode controller whose public contract is ensureSourceMode(view): Promise<boolean>. The current cast exists only inside it.
  • Create a title adapter that captures, applies, refreshes, and restores method overrides atomically. If Obsidian internals disappear, disable custom titles without destabilizing leaves.
  • Document obsidian-scripture as the canonical registry ID and mark scripture as deprecated-but-supported through 1.0.
  • Record the min-version decision: remain on 1.9.0; reassess declarative settings only when a separate release intentionally targets 1.13+.
Acceptance

No internal cast or method reassignment exists outside the two adapters. Unload always restores patched titles and clears timers. Missing internals produce a concise user-facing fallback rather than an exception.

06

Replace CSS debt with measured selectors

Work selector group by selector group; capture the DOM shape first, change one group, then run the matrix below.

  • Prefer direct child/sibling targeting for sup before adding JavaScript marker classes.
  • Where parent state is genuinely required, let BibleVerseDisplayManager add plugin-prefixed marker classes to the owning view and clean them up.
  • Replace !important using scoped specificity anchored to .bible, view-mode wrappers, or .scripture-sidebar-reading.
  • Keep an exception only when a named fixture fails without it, and document why the competing Obsidian/theme declaration cannot be beaten safely.
07

Cross-platform validation and debt closure

  • Run npm run check after every phase and once from a clean install.
  • Smoke-test the full AGENTS.md list in the existing desktop test vault.
  • Copy real main.js, manifest.json, and styles.css files—not the symlink—to a mobile-synced vault and repeat the mobile subset.
  • Update TECHNICAL-DEBT.md: remove completed items; keep only upstream-blocked adapters with the API/version trigger for re-evaluation.
Exit evidence

Attach the completed smoke matrix, final selector counts, file line counts, version-check output, build hashes, and attestation dry-run evidence. Do not create a tag or release without separate user authorization.

Canonical release design

Use a single .github/workflows/release.yaml with tag push and manual dispatch as entry points to the same job. Manual dispatch selects an already-versioned ref; it does not bump files or push a commit.

versioned source commit
        │
        ├── tag push: tag must equal manifest/package/lock/versions
        │
        └── manual dispatch: selected ref must already be version-consistent
                         │
                         ▼
                npm ci → npm run check
                         │
                         ▼
          verify main.js + manifest.json + styles.css
                         │
                         ▼
        actions/attest-build-provenance@v2 (all 3 files)
                         │
                         ▼
            create or update the matching GitHub release

Required workflow properties

  • Permissions: contents: write, id-token: write, attestations: write.
  • npm ci and pinned Node version; production bundle with no inline source map.
  • Version validator runs before any tag/release mutation.
  • Manual prerelease and notes inputs may be retained, but file mutation and git push are removed.
  • Required release assets remain exactly main.js, manifest.json, and styles.css.

Definition of done

  1. npm run check passes from a clean install, including version consistency.
  2. No released command ID, setting key, scriptureList syntax, callout Markdown, URI parameter, or ScriptureAPI method changes.
  3. main.ts, the Scripture list facade, and settings shell each have one clear responsibility; pure logic has focused unit tests.
  4. Unsupported Obsidian internals exist only in two documented adapters and fail safely.
  5. The API alias and minimum-version decisions are documented with explicit future review triggers.
  6. CSS selector debt is eliminated or each remaining exception has fixture-backed evidence.
  7. One release workflow validates versions, builds reproducibly, attests all assets, and never commits to the default branch.
  8. Desktop and mobile smoke matrices pass, and TECHNICAL-DEBT.md reflects only genuinely upstream-blocked work.
